# Settings live in the app; env vars only pin or lock; AI is bring-your-own

Everything a household might change is an in-app setting stored in SQLite and editable by anyone who can open cooka — printer and label preset, language, discard-reason mode, date meaning, default shelf life, preparation methods, next label number, AI provider. Environment variables cover only what must be known before cooka can serve a page (ports) plus the `COOKA_BASE_URL` pin, and a few optional **settings locks** (`COOKA_AI_API_KEY`, language, printer host): a locked setting wins over the stored value and shows read-only, "set by your server config". There is no first-run wizard; each setting is asked for when it is first needed (base URL before the first print, printer from the no-printer hint). Settings are reached from a small gear at the end of the top status line on every screen except cooking mode — not a fifth mode — and are not protected by a PIN: the network is the access boundary.

The **AI provider** is bring-your-own — key, model and provider — amending ADR 0009's fixed list: OpenAI, Anthropic, Gemini, or any OpenAI-compatible endpoint by base URL (Ollama, LM Studio, OpenRouter, vLLM, …), one per instance. The model is free text with suggestions, never a hard-coded list. Features needing image, audio or video input appear only when the provider is known to accept them; for OpenAI-compatible endpoints the user declares that. A Test action checks text, and — only when the user chooses — image and audio, showing the provider's own error.

We rejected env-var-only configuration (a household member cannot swap the label roll without editing `compose.yaml`) and a separate admin area. We rejected a fixed provider/model list (new models would wait for releases, and local models would be excluded) and supporting only the OpenAI-compatible protocol (Anthropic's and Gemini's native APIs do more, e.g. Gemini's YouTube-link input). We rejected encrypting the API key at rest: a generated key file next to the database protects nothing, and a startup passphrase breaks unattended restarts.

## Consequences

- The API key is write-only through UI and API (shown as `••••abcd`), stored in plain text in SQLite under `/data` (file mode 0600), present in the on-disk snapshots in `/data/backups/` but never in downloaded backups or user-facing exports (amended by ADR 0013), never logged, and masked in Test errors. A key set by `COOKA_AI_API_KEY` is never written to the database.
- The documented `compose.yaml` uses bridge networking; host networking is the documented option that enables mDNS printer discovery. In bridge mode, discovery sweeps the /24 of the device doing the setup (its LAN address from `X-Forwarded-For` in proxy mode, the connecting address in attached-cert mode); manual IP/host entry is always offered (needed over Tailscale or segmented networks). There is no subnet setting.
- Printer setup: candidates show model and serial; binding prints a test label, then offset nudge and darkness.
- The next label number can only be raised, never set at or below the highest number ever issued; the highest number is shown beside it.
- Settings sections: Printer & labels · Food defaults · Recipes & AI · Language · Data · System (version, update state, HTTPS mode, certificate expiry, base URL, printed hosts).
