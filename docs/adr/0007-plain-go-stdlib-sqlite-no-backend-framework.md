# Plain Go stdlib + SQLite, no backend framework

cooka's backend is plain Go: `net/http` with the Go 1.22 mux, `modernc.org/sqlite` (CGO-free) through `database/sql` with hand-written SQL, and forward-only numbered `.sql` migrations embedded in the binary and applied at startup by goose used as a library. SQLite runs in WAL mode with one writer connection and a small reader pool; all state lives in one `/data` volume. The backend speaks JSON under `/api` and embeds the frontend's build output; background work (e.g. shopping-list auto-clear), raw-TCP printing and recipe fetching run in the same process.

Realtime is one SSE stream (`GET /api/events`) carrying invalidation-only topic events — clients refetch, so there is no event schema to keep stable. Offline-queued writes need no sync engine: clients generate entry ids (UUIDv7) and create with idempotent PUTs, changes are absolute field patches (`checked: true`, never toggles), the server's arrival order decides except that a queued un-check older than the latest check-off is ignored, and writes to vanished entries return 404 and are dropped.

We rejected PocketBase (used as a Go framework). Its realtime, migrations, admin UI and backups are each small to build for cooka's needs, while it is 0.x with breaking changes in most minor releases, single-maintainer and recently moved off GitHub — a poor base for an app others self-host and fork. It also always creates `users`/`_superusers` collections and its admin UI requires a superuser account, contradicting cooka's no-accounts premise, and a generic record editor would bypass domain rules such as append-only stock history and label-number sequencing. We rejected sqlc and ORMs as unnecessary weight for a ~8-table domain, and down-migrations because restoring a backup is the rollback.
