# Backups: self-made zip snapshots; restores carry the label counter forward

cooka makes its own consistent backups instead of relying on self-hosters copying a live SQLite file. A **backup** is one zip (`cooka-backup-<date>-v<schema>.zip`) holding a `VACUUM INTO` copy of the database, the recipe image files, and a `manifest.json` (cooka version, schema version, created at, highest label number issued, every base URL printed with). cooka writes one to `/data/backups/` nightly at 03:00 server time and before every schema migration, keeping a fixed 7 daily, 4 weekly and 3 pre-migration (no setting). Settings → Data offers "Download backup now". Off-machine copies are the self-hoster's job: back up `/data` any way you like. The files in `/data/backups/` are consistent even when a raw copy of the live database is not. The last backup and its size show under Settings → System, and a failed nightly backup raises a one-line notice in the top status line.

Restoring (Settings → Data, upload a zip or pick a stored one) first takes a "before restore" backup, then replaces the database and images wholesale. Open screens reload via the event stream. There is no merge and no lock beyond who can open cooka.

- **Schema guard:** a backup from an older schema is restored, then migrated forward. A backup from a newer schema is refused ("update first"). Restoring the pre-migration backup on the pinned old image is the upgrade rollback, so there are no down-migrations.
- **Label counter and base URLs are carried forward:** after a restore, the next label number is the higher of the backup's and the current instance's highest issued, and the remembered base URLs are the union of both. Labels printed after the backup are still in the freezer, and reissuing their numbers would put two physical labels on one number. On a fresh or empty instance the restore screen shows the backup's highest number and suggests raising the next label number (+200) if anything was labelled since.
- **Labels the restore lost** are simply "Not found" when scanned and get re-labelled as new units. There is no "add it back" flow.
- **API key:** downloaded backups have it blanked. Only the on-disk snapshots in `/data/backups/` keep it, because anyone on the LAN can download a backup while the key is write-only in the UI. A restore without a key keeps the instance's current one. This amends ADR 0012.

Exports are for other tools and people, not for round-tripping: stock history CSV (one row per event), current stock CSV (one row per in-stock unit), and recipes as a zip of schema.org `Recipe` JSON-LD files with images (importable by Mealie, Tandoor and cooka's own import chain via paste). None of them contains the API key. There are no dedicated importers: CSVs are never re-imported (the stock history is append-only), and migration from Grocy/Mealie is out of scope.

We rejected docs-only backups ("stop the container, copy `/data`"; nobody stops the container, and a live WAL copy can be torn), built-in remote targets (S3/WebDAV credentials and surface), images as SQLite blobs (single-file backups, but amends ADR 0009 and bloats the database), and a JSON full dump (the backup zip is that).
